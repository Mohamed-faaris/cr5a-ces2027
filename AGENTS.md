# AGENTS.md

Repository-specific contracts; verify these before changing related code.

- **Keep this file high-signal:** record only non-obvious repository-specific facts, hidden dependencies, interface contracts, and failure-prone assumptions. Do not pad it with generic programming or tooling advice; update it when the codebase establishes a new fact an agent would otherwise need to rediscover.
- **React UI work:** read `cr5a_web/UI_GUIDELINES.md` for frontend-specific status, socket/store, motion-state, and URDF-viewer contracts.
- **Robot selection:** `dobot_bringup_v4/launch/dobot_bringup_ros2.launch.py` uses 1-based `current_robot` to select `node_info[current_robot - 1]` in `config/param.json`. Overrides are case-sensitive: `IP_address` and `DOBOT_TYPE`.
- **MoveIt/bridge interface:** bridge defaults are group `cr5_group`, base `dummy_link`, TCP link `Link6`, planning action `/move_action`, execution action `/execute_trajectory`. Keep `cr5a_ros_bridge/config/bridge.yaml` aligned with the MoveIt SRDF/launch configuration.
- **Planner profile contract:** motion-plan requests carry `pipeline_id` and `planner_id` in `MotionPlanRequest`; OMPL custom planner overrides use MoveIt `/set_planner_params` and persist in the running MoveGroup until overwritten or restarted. `ompl.max_planning_threads` is a planner-manager startup setting in `cr5_moveit/config/ompl_planning.yaml`, not a request field; restart MoveGroup after changing it. The visualizer profile UI preserves this distinction.
- **Joint-limit source:** `cr5_moveit/config/joint_limits.yaml` carries CR5A position limits as well as velocity/acceleration limits. `robot.get_joint_limits` exposes it to the visualizer, which merges configured position limits over URDF limits. Rebuild `cr5_moveit` after changing this file.
- **Bridge numeric contract:** REST/WebSocket outputs replace NaN/Infinity with `null` and log the source; all JSON request bodies reject NaN/Infinity (including overflowed exponents). Non-finite motion inputs are rejected, pose quaternions are normalized, and plans with invalid trajectories cannot execute. Execution also rejects missing, invalid, stale, or future-dated joint telemetry.
- **Two WebSockets, different protocols:** the web console uses the bridge application protocol at `/ws/v1` on port `8000`. Raw rosbridge is the separate standard protocol on port `9090`; do not point the UI at it. Frontend overrides are `VITE_BRIDGE_WS_URL` and `VITE_BRIDGE_TOKEN`.
- **Safety gates are intentional:** `allow_execution`, `allow_commands`, `allow_error_clear`, `generic_service_calls_enabled`, and `topic_publish_enabled` default to `false`. The bridge does not expose the safety-rated E-stop. Do not weaken these defaults as a side effect of feature work.
- **D415 wrist camera contract:** both tmux profiles start the real `realsense2_camera` driver as namespace `/cr5`, node `wrist_camera`, so the Calibration page's `/cr5/wrist_camera/color/camera_info` subscription matches. Color and depth are enabled, frame synchronization and aligned depth are enabled. The demo profile uses fake robot hardware but still expects a physically connected USB D415; do not add a guessed `Link6 -> wrist_camera_link` mount transform.
- **PGEA gripper contract:** the physical `pgea_gripper` node exposes `control_msgs/GripperCommand` at `/gripper_action_controller/gripper_cmd` plus `/pgea_gripper/get_status`, `/initialize`, and `/calibrate`. The PGEA-100-40-W range is 0–0.020 m per finger. `GripperCommand.max_effort` must remain 0 until a calibrated Newton-to-register-percent mapping exists. Physical transport defaults to `bringup`, which reuses the arm driver's single Dashboard connection; never start a second Dashboard client beside the arm driver. `dobot_simulation` also starts a fake action/status server for demo mode. The bridge exposes only dedicated `gripper.*` requests, gated by `gripper.allow_commands`, fresh arm status, and RobotMode 5 for motion.
- **Direct Dobot motion contract:** the visualizer uses robot.direct.check / robot.direct.execute over the shared /ws/v1 socket. MovJ targets are controller degrees but MoveIt collision samples use radians; MovL uses FK + sequential IK + state-validity samples and rejects IK branch jumps larger than the configured per-sample joint-step limit. Execute repeats validation and requires both robot.allow_commands and robot.allow_direct_movement. MovL is blocked unless direct_movement.controller_pose_frame_confirmed and explicit controller user/tool indices are configured after verifying controller TCP/user/tool frames against the MoveIt base/end-effector. Current/target joints use `cr5_moveit/config/joint_limits.yaml`; execution rejects scene changes or start-state drift, serializes direct moves until running-to-idle plus stable joint telemetry is confirmed, and latches uncertain results or bridge restarts for explicit operator recovery. Sampling is not the exact Dobot controller trajectory or a safety-rated guarantee.
- **Demo driver parity:** `cr5_moveit demo.launch.py` uses MoveIt fake hardware and starts `dobot_simulation`. The adapter reports `RobotStatus`, `RobotMode`, error services, and `ToolVectorActual`; TCP is calculated from `dummy_link -> Link6` TF in mm/degrees. It never opens a hardware socket. `RobotStatus.is_connected` stays false until fresh simulated joint states arrive. The demo UI is explicitly marked `SIMULATION`.
- **Simulation bridge profile:** `.tmuxp/cr5a-demo.yaml` starts the bridge with `simulation:=true`, which selects `bridge.simulation.yaml`. Only that isolated profile enables arm commands, error clearing, and MoveIt execution; generic service calls and arbitrary topic publishing remain disabled. The physical `bridge.yaml` keeps those arm-level command gates false but enables only the dedicated PGEA routes; never use the simulation profile with the physical driver.
- **Simulation command semantics:** simulated Stop cancels active fake `FollowJointTrajectory` goals. Pause also cancels an active goal; Continue clears the paused state but does not replay a cancelled trajectory, so plan again. Drag mode changes controller state only; it does not emulate gravity or physical hand-guiding. Set `/dobot_simulation` parameter `simulated_error_code` to a non-zero integer to test error reporting; ClearError/ResetRobot set it back to zero and leave the simulated robot disabled.
- **Launches are not interchangeable:** `dobot_gazebo.launch.py` spawns a separate Gazebo model and relays joint states, but does not connect MoveIt execution to Gazebo. Do not run it alongside `cr5_moveit demo.launch.py` in the same ROS domain because that creates a second, unlinked CR5A TF tree. Physical operation uses `dobot_bringup_ros2.launch.py` plus `cr5_moveit dobot_moveit.launch.py`; never run fake and physical stacks together in one ROS domain.
- **tmux pane contract:** `.tmuxp/cr5a-demo.yaml` and `.tmuxp/cr5a-hardware.yaml` keep interactive Humble shell panes separate from running service/monitor panes. Shells source `/opt/ros/humble/setup.bash` and `install/setup.bash`; route every pane through `.tmuxp/log-pane.sh` so its output lands in `/root/cr5a_ws/logs/tmux/<session-timestamp>/`.
- **Runtime assumptions:** this checkout is built in the Humble container at `/root/cr5a_ws`; the host's Jazzy environment is not the build environment.
